## STEP 1 — Observation

사용자는 길이 값을 특정 단위로 입력하고, 프로그램은 이를 지원되는 다른 길이 단위로 일관되게 변환해 출력해야 하는 상황에 있다. 현재 문제는 단순 계산기를 만드는 것이 아니라, 단위가 늘어나고 입력 형식이 다양해지고 출력 요구가 바뀌어도 핵심 변환 규칙이 흔들리지 않도록 요구사항의 경계를 먼저 정리하는 데 초점이 있다.

길이 변환을 다루는 이유는 결과가 직관적으로 검증 가능하면서도, 단위 간 기준값·비율·입력 형식·출력 형식·확장성 같은 설계 요소를 함께 드러내기 좋기 때문이다.

이 문제는 OCP/SRP를 통해 변경에 강한 구조를 훈련하고, 입력 검증을 통해 잘못된 사용을 통제하며, 설정 외부화와 동적 단위 등록을 통해 코드 변경 없이 정책을 확장하는 사고를 연습하는 맥락에서 등장한다. 또한 출력 포맷 선택은 같은 계산 결과를 여러 소비자에게 다르게 제공해야 하는 책임 분리의 필요성을 보여준다.

## STEP 2 — Why #1: 정확한 변환 결과가 왜 중요한가?

정확한 변환 결과는 이 프로그램의 신뢰 기준이다. 단위 변환은 사용자가 계산 결과 자체를 의사결정의 근거로 삼는 문제이므로, 작은 오차나 잘못된 비율도 전체 프로그램의 목적을 무너뜨릴 수 있다.

또한 변환 기준이 하나로 고정되지 않으면 같은 입력이 상황마다 다른 결과를 만들 수 있다. 따라서 기준 단위, 변환 비율, 반올림 정책, 출력 정밀도는 명확하게 정의되어야 한다.

## STEP 3 — Why #2: 수동 계산이 아닌 프로그램(+테스트)인 이유?

수동 계산은 한두 번의 예시에는 충분하지만, 단위가 늘어나거나 입력이 다양해지면 반복성과 일관성을 보장하기 어렵다. 프로그램은 동일한 규칙을 반복 적용할 수 있고, 잘못된 입력을 체계적으로 거부할 수 있으며, 새로운 단위가 추가되어도 같은 방식으로 검증할 수 있다.

테스트가 필요한 이유는 변환 로직이 겉보기에는 단순해도 기준 비율, 역변환, 단위 간 교차 변환, 잘못된 입력 처리에서 오류가 쉽게 숨어들기 때문이다. 테스트는 “지금 맞다”가 아니라 “변경 후에도 계속 맞다”를 보장하기 위한 장치다.

## STEP 4 — Why #3: 계약을 먼저 고정하려는 이유?

계약을 먼저 고정하는 이유는 구현 전에 무엇을 맞다고 볼지 합의해야 하기 때문이다. 입력 형식, 지원 단위, 변환 기준, 오류 처리, 출력 형식이 불명확하면 구현은 빠르게 진행되어도 검증 기준이 흔들린다.

계약은 설계의 자유도를 제한하기 위한 것이 아니라, 변경 가능한 부분과 변경되면 안 되는 부분을 구분하기 위한 기준이다. 특히 OCP/SRP, 설정 외부화, 동적 등록, 출력 포맷 선택은 모두 확장 지점이므로, 먼저 불변 조건과 책임 경계를 정해야 확장이 누적되어도 프로그램의 의미가 유지된다.

## STEP 5 — 문제 정의

### 1) 표면 문제

사용자가 입력한 길이 값을 다른 길이 단위로 변환해 출력해야 한다. 현재는 meter, feet, yard 간 변환을 정확히 처리하는 것이 기본 목표다.

### 2) 개선된 정의

이 문제는 길이 단위와 값을 입력받아, 정의된 변환 기준에 따라 모든 대상 단위의 값을 계산하고, 선택된 출력 형식으로 일관되게 제공하는 변환 시스템을 정의하는 것이다. 시스템은 잘못된 입력, 음수 값, 알 수 없는 단위를 명확히 거부해야 한다. 새로운 단위나 변환 비율이 추가되더라도 기존 변환 규칙과 검증된 동작이 깨지지 않아야 한다. 변환 비율은 코드 내부에 고정된 지식이 아니라 변경 가능한 설정 또는 등록 정보로 취급되어야 한다. 계산 책임, 입력 검증 책임, 단위 관리 책임, 출력 표현 책임은 서로 섞이지 않아야 한다. 테스트는 핵심 변환 결과와 실패 조건을 계약으로 고정하여 이후 변경의 안전망 역할을 해야 한다.

### 3) 핵심 Invariant

- 같은 입력과 같은 변환 설정은 항상 같은 변환 결과를 생성해야 한다.
- 지원되지 않는 단위는 변환 대상이 될 수 없으며 명확히 실패해야 한다.
- 음수 길이 값과 잘못된 입력 형식은 유효한 변환으로 처리되면 안 된다.
- 단위 간 직접 비율이 없더라도 기준 단위를 통해 일관된 결과를 계산해야 한다.
- 출력 형식이 달라져도 변환 값의 의미와 정확성은 변하지 않아야 한다.

### 4) 훈련하려는 사고 능력

- 요구사항에서 불변 조건과 확장 지점을 분리하는 능력
- 책임을 나누어 변경 영향을 좁히는 설계 사고
- 테스트를 통해 동작 계약을 먼저 고정하는 사고

## 1) Entity(Domain) 설계

### 1.1 개념 목록과 SRP

- `UnitId`: 단위 식별자. 소문자 영문 단위명만 표현한다.
- `Measurement`: 값과 단위의 조합. 길이 값은 0 이상이어야 한다.
- `ConversionRate`: 기준 단위 대비 변환 비율. 비율은 0보다 커야 한다.
- `UnitRegistry`: 등록된 단위와 비율을 관리한다.
- `ConversionService`: 하나의 입력 측정값을 다른 단위 값들로 변환한다.
- `ConversionResult`: 원본 측정값, 대상 단위, 변환값을 표현한다.
- `DomainError`: 도메인 규칙 위반을 실패 사유로 표현한다.

### 1.2 Invariants

- 단위명은 정규식 `^[a-z][a-z0-9_]{0,31}$`를 만족해야 한다.
- 길이 값은 `0 <= value <= 1,000,000,000` 범위여야 한다.
- 변환 비율은 `rateToMeter > 0`이어야 한다.
- 동일한 단위명은 한 번만 등록될 수 있다.
- 변환 계산은 항상 기준 단위인 `meter`를 경유한다.
- 동일 입력, 동일 등록 상태, 동일 정밀도에서는 결과가 동일해야 한다.
- 변환 결과 비교 허용 오차는 Domain 테스트에서 `0.00001` 이하여야 한다.

### 1.3 유스케이스

- 등록된 단위 목록 조회
- 단일 입력 측정값 검증
- 입력 단위에서 모든 다른 단위로 변환
- 입력 단위에서 특정 대상 단위로 변환
- 새로운 단위와 기준 비율 등록
- 중복 단위 등록 거부
- 알 수 없는 단위 변환 거부

### 1.4 Domain API + 실패 조건

- `CreateUnitId(name) -> UnitId | DomainError`
  - 실패: 빈 문자열
  - 실패: 대문자 포함
  - 실패: 공백 포함
  - 실패: 32자 초과
  - 실패: 첫 글자가 영문 소문자가 아님

- `CreateMeasurement(unitId, value) -> Measurement | DomainError`
  - 실패: 값이 숫자가 아님
  - 실패: 값이 음수
  - 실패: 값이 `1,000,000,000` 초과

- `RegisterUnit(unitId, rateToMeter) -> UnitRegistry | DomainError`
  - 실패: `rateToMeter <= 0`
  - 실패: 이미 등록된 단위
  - 실패: 기준 단위 `meter`를 다른 비율로 재등록

- `Convert(input, targetUnitId) -> ConversionResult | DomainError`
  - 실패: 입력 단위 미등록
  - 실패: 대상 단위 미등록
  - 실패: 입력 측정값이 Domain invariant 위반

- `ConvertToAll(input) -> ConversionResultList | DomainError`
  - 실패: 입력 단위 미등록
  - 성공: 입력 단위를 제외한 모든 등록 단위 결과 반환
  - 성공: 반환 순서는 단위 등록 순서와 동일

### 1.5 Domain 단위 테스트 설계

RED 우선 테스트 목록:

- `meter 1.0을 feet로 변환하면 3.28084가 된다`
- `meter 1.0을 yard로 변환하면 1.09361이 된다`
- `feet 3.28084를 meter로 변환하면 1.0이 된다`
- `yard 1.09361을 meter로 변환하면 1.0이 된다`
- `feet에서 yard 변환은 meter 기준 경유 결과와 같다`
- `음수 Measurement 생성은 실패한다`
- `0 값 Measurement 생성은 성공한다`
- `알 수 없는 입력 단위 변환은 실패한다`
- `알 수 없는 대상 단위 변환은 실패한다`
- `중복 단위 등록은 실패한다`
- `0 이하 변환 비율 등록은 실패한다`
- `ConvertToAll은 입력 단위를 결과에서 제외한다`
- `ConvertToAll 결과 순서는 등록 순서를 따른다`

## 2) Boundary 설계

### 2.1 시나리오: 입력 → 검증 → 실행 → 출력

1. Boundary가 원문 입력을 받는다.
2. Boundary가 입력 형식 `unit:value`를 검증한다.
3. Boundary가 단위 문자열과 값 문자열을 분리한다.
4. Boundary가 값 문자열을 숫자로 파싱한다.
5. Boundary가 Domain 요청 모델로 변환한다.
6. Control이 Domain 변환 유스케이스를 실행한다.
7. Boundary가 성공 결과를 선택된 출력 포맷으로 직렬화한다.
8. Boundary가 실패 결과를 고정된 Error schema로 직렬화한다.

### 2.2 외부 계약: Input / Output / Error schema

Input schema:

- `rawInput`: 필수 문자열
- 허용 형식: `unit:value`
- `unit`: `^[a-z][a-z0-9_]{0,31}$`
- `value`: 십진수 숫자
- `value` 범위: `0` 이상 `1,000,000,000` 이하
- 공백 정책: 전체 앞뒤 공백은 제거, 단위명 내부 공백은 실패
- 예: `meter:2.5`

Output schema:

- `sourceUnit`: 입력 단위명
- `sourceValue`: 입력 숫자
- `results`: 1개 이상의 변환 결과 목록
- 각 결과:
  - `targetUnit`
  - `convertedValue`
  - `displayText`
- `convertedValue` 내부 정밀도: 소수점 5자리 이상 검증 가능
- 기본 표시 정밀도: 소수점 1자리
- 출력 포맷: `plain`, `json`, `csv`, `table`

Error schema:

- `errorCode`: 고정된 오류 코드
- `message`: 사용자 표시 메시지
- `field`: 오류가 발생한 필드
- `input`: 원문 입력
- `recoverable`: 사용자가 입력을 고쳐 재시도할 수 있으면 `true`

오류 코드:

- `INVALID_FORMAT`
- `INVALID_UNIT_NAME`
- `INVALID_VALUE`
- `NEGATIVE_VALUE`
- `UNKNOWN_UNIT`
- `DUPLICATE_UNIT`
- `INVALID_RATE`
- `UNSUPPORTED_OUTPUT_FORMAT`

### 2.3 Boundary 계약 테스트

Domain Mock 가정 테스트:

- `meter:2.5` 입력 시 Domain에 `unit=meter`, `value=2.5` 요청을 전달한다.
- ` meter:2.5 ` 입력 시 앞뒤 공백 제거 후 Domain에 전달한다.
- `meter` 입력 시 Domain을 호출하지 않고 `INVALID_FORMAT`을 반환한다.
- `meter:` 입력 시 Domain을 호출하지 않고 `INVALID_VALUE`를 반환한다.
- `meter:-1` 입력 시 Domain을 호출하지 않고 `NEGATIVE_VALUE`를 반환한다.
- `Meter:1` 입력 시 Domain을 호출하지 않고 `INVALID_UNIT_NAME`을 반환한다.
- Domain이 `UNKNOWN_UNIT`을 반환하면 Boundary는 동일한 `errorCode`를 유지한다.
- `json` 포맷 요청 시 결과 필드명이 계약과 일치한다.
- `csv` 포맷 요청 시 첫 줄은 헤더를 포함한다.
- `plain` 포맷 요청 시 각 결과는 한 줄에 하나씩 출력된다.

### 2.4 에러 메시지 규칙

문구 패턴:

- `INVALID_FORMAT`: `Invalid input format. Expected "<unit>:<value>".`
- `INVALID_UNIT_NAME`: `Invalid unit name: "<unit>". Use lowercase letters, digits, or underscore.`
- `INVALID_VALUE`: `Invalid value: "<value>". Use a numeric length value.`
- `NEGATIVE_VALUE`: `Invalid value: "<value>". Length must be zero or greater.`
- `UNKNOWN_UNIT`: `Unknown unit: "<unit>". Register the unit before conversion.`
- `DUPLICATE_UNIT`: `Duplicate unit: "<unit>". Unit names must be unique.`
- `INVALID_RATE`: `Invalid rate: "<rate>". Rate must be greater than zero.`
- `UNSUPPORTED_OUTPUT_FORMAT`: `Unsupported output format: "<format>".`

검증 규칙:

- 오류 메시지는 항상 마침표로 끝난다.
- 사용자 입력값은 큰따옴표로 감싼다.
- `errorCode`와 메시지 패턴은 1:1로 대응한다.
- 같은 오류 조건은 항상 같은 `errorCode`를 반환한다.

## 3) Data 설계

### 3.1 목적

Data 레이어는 단위 정의와 변환 비율을 Domain이 사용할 수 있는 등록 정보로 제공한다. Data 레이어는 변환 계산을 수행하지 않는다. Data 레이어는 저장소 형식 변경이 Domain 규칙에 영향을 주지 않도록 격리한다.

### 3.2 인터페이스 계약

이름만 제안:

- `UnitDefinitionRepository`
- `UnitDefinitionLoader`
- `UnitDefinitionWriter`
- `UnitDefinitionValidator`
- `UnitRegistryProvider`

### 3.3 InMemory vs File(JSON/YAML) 비교 + 추천

InMemory:

- 장점: 테스트가 빠르다.
- 장점: 외부 파일 실패가 없다.
- 장점: Domain 테스트와 Boundary 계약 테스트에 적합하다.
- 단점: 설정 외부화 요구를 충족하지 못한다.
- 단점: 프로그램 재시작 후 동적 등록 상태를 보존하지 못한다.

File(JSON/YAML):

- 장점: 설정 외부화 요구를 충족한다.
- 장점: 단위 추가를 코드 변경 없이 검증할 수 있다.
- 장점: 실제 사용자 시나리오와 통합 테스트에 적합하다.
- 단점: 파일 없음, 파싱 실패, 스키마 오류를 별도로 다뤄야 한다.
- 단점: 테스트에서 고정 fixture 관리가 필요하다.

추천: File(JSON)

이유: 요구사항에 변환 비율 외부화와 동적 단위 등록이 포함되어 있으므로, 기본 Data 전략은 파일 기반이어야 한다. JSON은 숫자, 문자열, 목록 구조를 명확히 표현하며 테스트 fixture의 기대값 비교가 YAML보다 단순하다. InMemory는 운영 기본값이 아니라 테스트 대역과 빠른 개발용 저장소로 제한한다.

### 3.4 Data 레이어 테스트

- 유효한 JSON 단위 정의를 읽으면 `meter`, `feet`, `yard`가 로드된다.
- `meter`의 `rateToMeter`가 `1.0`이 아니면 로딩 실패다.
- 중복 단위명이 있으면 로딩 실패다.
- `rateToMeter <= 0`인 항목이 있으면 로딩 실패다.
- 단위명이 규칙을 위반하면 로딩 실패다.
- 필수 필드가 없으면 로딩 실패다.
- 빈 단위 목록은 로딩 실패다.
- 파일이 없으면 `DATA_SOURCE_NOT_FOUND`를 반환한다.
- JSON 파싱 실패는 `DATA_PARSE_ERROR`를 반환한다.
- 동적 등록 저장 후 재로딩하면 동일한 단위와 비율이 복원된다.

## 4) Integration & Verification

### 4.1 의존성 방향 포함 흐름

- Boundary는 Control에 의존한다.
- Control은 Domain API에 의존한다.
- Control은 Data 인터페이스에 의존한다.
- Domain은 Boundary에 의존하지 않는다.
- Domain은 Data 저장소 구현에 의존하지 않는다.
- File Data Adapter는 Data 인터페이스를 구현한다.
- InMemory Data Adapter는 Data 인터페이스를 구현한다.

실행 흐름:

1. Boundary가 사용자 입력과 출력 포맷을 받는다.
2. Boundary가 외부 입력 계약을 검증한다.
3. Control이 Data 인터페이스를 통해 단위 정의를 로드한다.
4. Control이 Domain Registry를 구성한다.
5. Control이 Domain 변환 유스케이스를 호출한다.
6. Boundary가 결과 또는 오류를 외부 계약으로 변환한다.

### 4.2 통합 테스트 시나리오

정상 시나리오:

- `meter:2.5`, 기본 단위 3개, `plain` 출력 시 feet와 yard 결과가 각각 1줄씩 출력된다.
- `feet:3.28084`, `json` 출력 시 meter 결과의 `convertedValue`는 `1.0` 허용 오차 이내다.
- JSON 설정에 `cubit=0.4572 meter`를 추가하면 `meter:1` 입력 결과에 `cubit` 변환이 포함된다.

실패 시나리오:

- `meter:-1` 입력 시 `NEGATIVE_VALUE`가 반환되고 Domain 변환은 실행되지 않는다.
- `inch:1` 입력 시 `UNKNOWN_UNIT`이 반환된다.
- 설정 파일에 중복 단위가 있으면 변환 실행 전에 로딩 실패가 반환된다.
- 설정 파일의 `feet` 비율이 `0`이면 `INVALID_RATE`가 반환된다.
- 출력 포맷이 `xml`이면 `UNSUPPORTED_OUTPUT_FORMAT`이 반환된다.

### 4.3 회귀 보호 규칙

- `1 meter = 3.28084 feet`는 변경 금지 기준값으로 테스트한다.
- `1 meter = 1.09361 yard`는 변경 금지 기준값으로 테스트한다.
- feet와 yard 간 변환은 직접 상수 없이 meter 기준 경유 결과로 테스트한다.
- 에러 코드는 문자열 변경을 회귀로 간주한다.
- 에러 메시지 패턴 변경은 계약 테스트 실패로 간주한다.
- 출력 포맷별 필드명 변경은 계약 테스트 실패로 간주한다.
- 새 단위 추가 시 기존 단위 변환 테스트가 모두 통과해야 한다.

### 4.4 커버리지 목표

- Domain: 라인 커버리지 90% 이상, 분기 커버리지 85% 이상
- Boundary: 라인 커버리지 85% 이상, 오류 분기 커버리지 90% 이상
- Data: 라인 커버리지 80% 이상, 실패 케이스 커버리지 90% 이상
- Integration: 핵심 정상 흐름 3개 이상, 실패 흐름 5개 이상

### 4.5 Traceability Matrix

- Concept: `UnitId`
  - Rule: 단위명은 `^[a-z][a-z0-9_]{0,31}$`를 만족한다.
  - UseCase: 입력 단위 검증, 신규 단위 등록
  - Contract: `INVALID_UNIT_NAME`
  - Test: 대문자 단위명은 Boundary에서 거부된다.
  - Component: Boundary, Domain

- Concept: `Measurement`
  - Rule: 값은 `0` 이상 `1,000,000,000` 이하다.
  - UseCase: 입력 측정값 검증
  - Contract: `INVALID_VALUE`, `NEGATIVE_VALUE`
  - Test: `meter:-1`은 실패하고 `meter:0`은 성공한다.
  - Component: Boundary, Domain

- Concept: `ConversionRate`
  - Rule: 비율은 `0`보다 크다.
  - UseCase: 단위 정의 로드, 신규 단위 등록
  - Contract: `INVALID_RATE`
  - Test: `rateToMeter=0`인 단위 정의는 실패한다.
  - Component: Data, Domain

- Concept: `UnitRegistry`
  - Rule: 동일 단위명은 한 번만 등록된다.
  - UseCase: 기본 단위 로드, 동적 단위 등록
  - Contract: `DUPLICATE_UNIT`
  - Test: 같은 단위명을 두 번 등록하면 실패한다.
  - Component: Domain, Data

- Concept: `ConversionService`
  - Rule: 모든 변환은 meter 기준을 경유한다.
  - UseCase: 단일 대상 변환, 전체 단위 변환
  - Contract: `UNKNOWN_UNIT`
  - Test: feet에서 yard 변환은 feet→meter→yard 결과와 같다.
  - Component: Domain

- Concept: `OutputFormatter`
  - Rule: 포맷이 달라도 변환값 의미는 동일하다.
  - UseCase: plain/json/csv/table 출력
  - Contract: `UNSUPPORTED_OUTPUT_FORMAT`
  - Test: 같은 입력의 plain과 json 결과는 동일한 대상 단위와 값을 가진다.
  - Component: Boundary

- Concept: `UnitDefinitionRepository`
  - Rule: 저장소 오류는 변환 오류와 구분된다.
  - UseCase: 설정 외부화, 동적 등록 복원
  - Contract: `DATA_SOURCE_NOT_FOUND`, `DATA_PARSE_ERROR`
  - Test: 파일 없음과 JSON 파싱 실패는 서로 다른 오류 코드를 반환한다.
  - Component: Data, Control

## RED 단계 테스트 케이스 제목

### 파싱

1. `meter:2.5` 입력은 단위 `meter`와 값 `2.5`로 파싱된다.  
   Invariant: `InputFormatIsUnitColonValue`

2. 앞뒤 공백이 있는 ` meter:2.5 ` 입력은 동일한 의미로 파싱된다.  
   Invariant: `OuterWhitespaceIsIgnored`

3. 콜론이 없는 `meter2.5` 입력은 거부된다.  
   Invariant: `InputMustContainSingleColon`

4. 콜론이 2개 이상인 `meter:2.5:extra` 입력은 거부된다.  
   Invariant: `InputMustContainSingleColon`

5. 단위가 비어 있는 `:2.5` 입력은 거부된다.  
   Invariant: `UnitNameMustBePresent`

6. 값이 비어 있는 `meter:` 입력은 거부된다.  
   Invariant: `ValueMustBePresent`

7. 대문자가 포함된 `Meter:2.5` 입력은 거부된다.  
   Invariant: `UnitNameMustMatchPattern`

8. 숫자가 아닌 값 `meter:abc` 입력은 거부된다.  
   Invariant: `ValueMustBeNumeric`

### 음수·0

9. `meter:0` 입력은 유효한 길이로 처리된다.  
   Invariant: `LengthValueCanBeZero`

10. `feet:0` 입력의 모든 변환 결과는 `0`이다.  
    Invariant: `ZeroLengthConvertsToZero`

11. `yard:-1` 입력은 변환 전에 거부된다.  
    Invariant: `LengthValueMustNotBeNegative`

12. `meter:-0.01` 입력은 변환 전에 거부된다.  
    Invariant: `LengthValueMustNotBeNegative`

### 미지원 단위

13. `inch:1` 입력은 `UNKNOWN_UNIT` 오류로 실패한다.  
    Invariant: `InputUnitMustBeRegistered`

14. 대상 단위가 등록되어 있지 않으면 단일 대상 변환은 실패한다.  
    Invariant: `TargetUnitMustBeRegistered`

15. 등록되지 않은 단위 실패 시 변환 결과 목록은 생성되지 않는다.  
    Invariant: `FailedConversionProducesNoResults`

16. 미지원 단위 오류 메시지는 입력 단위명을 포함한다.  
    Invariant: `ErrorMessageIncludesInvalidToken`

### 비율 정확도

17. `meter:1`을 feet로 변환하면 `3.28084`와 허용 오차 이내다.  
    Invariant: `MeterToFeetRateIsFixed`

18. `meter:1`을 yard로 변환하면 `1.09361`과 허용 오차 이내다.  
    Invariant: `MeterToYardRateIsFixed`

19. `feet:3.28084`를 meter로 변환하면 `1.0`과 허용 오차 이내다.  
    Invariant: `ReverseConversionUsesSameBaseRate`

20. `yard:1.09361`을 meter로 변환하면 `1.0`과 허용 오차 이내다.  
    Invariant: `ReverseConversionUsesSameBaseRate`

21. feet에서 yard 변환은 feet→meter→yard 기준 결과와 일치한다.  
    Invariant: `CrossUnitConversionUsesMeterAsBase`

22. 동일 입력과 동일 등록 상태는 반복 실행해도 동일 결과를 만든다.  
    Invariant: `ConversionIsDeterministic`

### 동적 등록

23. `cubit` 단위를 `0.4572 meter` 비율로 등록하면 변환 대상 목록에 포함된다.  
    Invariant: `RegisteredUnitParticipatesInConversion`

24. 이미 등록된 `meter` 단위를 다시 등록하면 실패한다.  
    Invariant: `UnitNameMustBeUnique`

25. `rateToMeter`가 `0`인 단위 등록은 실패한다.  
    Invariant: `RateToMeterMustBePositive`

26. `rateToMeter`가 음수인 단위 등록은 실패한다.  
    Invariant: `RateToMeterMustBePositive`

27. 동적 등록 후 기존 `meter`, `feet`, `yard` 변환 결과는 변하지 않는다.  
    Invariant: `AddingUnitDoesNotChangeExistingRates`

28. 잘못된 단위명으로 동적 등록하면 실패한다.  
    Invariant: `DynamicUnitNameMustMatchPattern`

### 출력 직렬화: JSON

29. JSON 출력은 `sourceUnit`, `sourceValue`, `results` 필드를 포함한다.  
    Invariant: `JsonOutputSchemaIsStable`

30. JSON 출력의 각 결과는 `targetUnit`과 `convertedValue`를 포함한다.  
    Invariant: `JsonResultItemSchemaIsStable`

31. JSON 출력에서 숫자 값은 문자열이 아니라 숫자로 직렬화된다.  
    Invariant: `JsonNumericValuesRemainNumeric`

32. JSON 출력 실패 응답은 `errorCode`, `message`, `field`를 포함한다.  
    Invariant: `JsonErrorSchemaIsStable`

### 출력 직렬화: CSV

33. CSV 출력 첫 줄은 고정 헤더 `sourceUnit,sourceValue,targetUnit,convertedValue`를 가진다.  
    Invariant: `CsvHeaderIsStable`

34. CSV 출력은 변환 결과 1개당 데이터 행 1개를 생성한다.  
    Invariant: `CsvRowCountMatchesResultCount`

35. CSV 출력의 행 순서는 Domain 변환 결과 순서를 유지한다.  
    Invariant: `CsvPreservesResultOrder`

36. CSV 실패 응답은 오류 코드와 메시지를 포함한 단일 행으로 직렬화된다.  
    Invariant: `CsvErrorOutputIsStable`

### 출력 직렬화: 표

37. 표 출력은 `Source`, `Value`, `Target`, `Converted` 열을 포함한다.  
    Invariant: `TableHeaderIsStable`

38. 표 출력은 변환 결과 1개당 본문 행 1개를 생성한다.  
    Invariant: `TableRowCountMatchesResultCount`

39. 표 출력의 숫자 표시 정밀도는 설정된 표시 정밀도를 따른다.  
    Invariant: `TableDisplayPrecisionIsConsistent`

40. 표 실패 응답은 오류 코드와 메시지를 같은 표 구조 안에 표시한다.  
    Invariant: `TableErrorOutputIsStable`

# Level 3 User Stories

## 1. 입력 검증

**Story:**  
C++/클린 아키텍처 학습자로서, 잘못된 입력이 변환 로직에 들어가기 전에 거부되기를 원한다. 그래야 Boundary 책임과 Domain 책임을 분리해 학습할 수 있다.

### Acceptance Criteria

- [ ] `unit:value` 형식이 아니면 실패한다.
- [ ] 단위명이 비어 있으면 실패한다.
- [ ] 값이 비어 있으면 실패한다.
- [ ] 값이 숫자가 아니면 실패한다.
- [ ] 음수 값은 실패한다.
- [ ] 실패 시 변환 결과는 생성되지 않는다.
- [ ] 실패 시 고정된 오류 코드와 메시지 패턴을 반환한다.

## 2. 레지스트리·OCP

**Story:**  
학습자로서, 단위 목록과 변환 비율이 레지스트리를 통해 관리되기를 원한다. 그래야 새 단위 추가가 기존 변환 로직 수정으로 이어지지 않는지 확인할 수 있다.

### Acceptance Criteria

- [ ] 등록된 단위만 변환에 사용할 수 있다.
- [ ] 동일 단위명 중복 등록은 실패한다.
- [ ] 단위 추가 후 기존 단위 변환 결과는 변하지 않는다.
- [ ] 전체 변환 결과에는 입력 단위를 제외한 등록 단위가 포함된다.
- [ ] 새 단위 추가 시 기존 테스트 기대값을 수정하지 않는다.

## 3. 환산 정확도

**Story:**  
학습자로서, meter, feet, yard 간 환산이 고정 비율을 기준으로 정확히 계산되기를 원한다. 그래야 리팩터링 후에도 핵심 도메인 규칙이 보존되는지 확인할 수 있다.

### Acceptance Criteria

- [ ] `1 meter = 3.28084 feet`를 만족한다.
- [ ] `1 meter = 1.09361 yard`를 만족한다.
- [ ] feet에서 meter로의 역변환은 허용 오차 이내로 일치한다.
- [ ] yard에서 meter로의 역변환은 허용 오차 이내로 일치한다.
- [ ] feet와 yard 간 변환은 meter 기준 경유 결과와 일치한다.
- [ ] 동일 입력과 동일 설정은 항상 동일 결과를 만든다.

## 4. 출력 포맷

**Story:**  
학습자로서, 같은 변환 결과를 JSON, CSV, 표 형식으로 출력할 수 있기를 원한다. 그래야 계산 책임과 표현 책임을 분리해 검증할 수 있다.

### Acceptance Criteria

- [ ] JSON 출력은 고정된 최상위 필드를 가진다.
- [ ] CSV 출력은 고정 헤더를 가진다.
- [ ] 표 출력은 고정 열 이름을 가진다.
- [ ] 모든 출력 포맷은 동일한 변환 결과 수를 표현한다.
- [ ] 출력 포맷 변경은 변환값을 변경하지 않는다.
- [ ] 지원하지 않는 출력 포맷은 실패한다.

## 5. 설정 로드 실패

**Story:**  
학습자로서, 단위 설정 파일에 문제가 있을 때 변환이 시작되기 전에 명확히 실패하기를 원한다. 그래야 Data 레이어 실패와 Domain 실패를 구분할 수 있다.

### Acceptance Criteria

- [ ] 설정 파일이 없으면 데이터 소스 오류로 실패한다.
- [ ] 설정 파일 형식이 잘못되면 파싱 오류로 실패한다.
- [ ] 필수 필드가 없으면 스키마 오류로 실패한다.
- [ ] 중복 단위가 있으면 로드 실패한다.
- [ ] 변환 비율이 0 이하이면 로드 실패한다.
- [ ] 설정 로드 실패 시 변환은 실행되지 않는다.

## 6. 동적 단위 등록

**Story:**  
학습자로서, 실행 중 새 단위와 기준 비율을 등록할 수 있기를 원한다. 그래야 확장 가능한 설계가 실제 동작으로 이어지는지 확인할 수 있다.

### Acceptance Criteria

- [ ] 새 단위명과 meter 기준 비율을 등록할 수 있다.
- [ ] 등록된 새 단위는 이후 변환 대상에 포함된다.
- [ ] 잘못된 단위명은 등록 실패한다.
- [ ] 0 이하 비율은 등록 실패한다.
- [ ] 이미 존재하는 단위명은 등록 실패한다.
- [ ] 동적 등록 후 기존 단위 변환 결과는 유지된다.

    When the converter loads unit definitions
    Then the load fails

    Given the base unit is "meter"

    And the result includes a conversion to "yard"

    Given the user input is "meter:2.5"
    When the conversion is requested
    Then the output source unit is "meter"
    And the output source value is 2.5
    And every result row is associated with source unit "meter"
    And every result row is associated with source value 2.5

  Scenario: Convert one meter to feet using the fixed README rate
    Given the user input is "meter:1"
    When the conversion is requested
    Then the conversion to "feet" is 3.28084 within tolerance 0.00001

  Scenario: Convert one meter to yard using the fixed README rate
    Given the user input is "meter:1"
    When the conversion is requested
    Then the conversion to "yard" is 1.09361 within tolerance 0.00001

  Scenario: Convert feet to yard through the meter base rate
    Given the user input is "feet:3.28084"
    When the conversion is requested
    Then the conversion to "meter" is 1.0 within tolerance 0.00001
    And the conversion to "yard" is 1.09361 within tolerance 0.00001

  Scenario: Reject malformed decimal value
    Given the user input is "meter:2.5.1"
    When the conversion is requested
    Then the conversion fails
    And the error code is "INVALID_VALUE"
    And no conversion result is produced

  Scenario: Reject negative input before conversion
    Given the user input is "yard:-1"
    When the conversion is requested
    Then the conversion fails
    And the error code is "NEGATIVE_VALUE"
    And no conversion result is produced

  Scenario: Reject unknown unit
    Given the user input is "inch:1"
    When the conversion is requested
    Then the conversion fails
    And the error code is "UNKNOWN_UNIT"
    And no conversion result is produced

## 1. 프로젝트 개요

### 1.1 한 줄 목적문

UnitConverter_05는 C++/클린 아키텍처 학습자가 길이 단위 변환 문제를 통해 계약 정의, 테스트 우선 검증, 레이어 분리를 학습하기 위한 C++17 기반 단위 변환 학습 시스템이다.

### 1.2 배경 및 문제 정의

학습자는 meter, feet, yard 간 길이 변환 요구사항을 처음에는 단순 계산 문제로 인식하기 쉽다. 그러나 이 프로젝트의 핵심은 변환 알고리즘이 아니라 입력 형식, 오류 정책, 기준 비율, 출력 표현, 단위 확장 방식을 테스트 가능한 계약으로 고정하는 것이다.

기본 요구사항은 `meter`, `feet`, `yard` 변환을 다루지만, 품질 요구사항은 OCP/SRP, 입력 검증, 설정 외부화, 동적 단위 등록, 출력 포맷 선택까지 포함한다. 따라서 이 프로젝트는 계산 결과뿐 아니라 Boundary, Control, Entity 책임 분리와 회귀 보호 정책을 학습 대상으로 삼는다.

### 1.3 목표

- Domain 테스트는 라인 커버리지 90% 이상, 분기 커버리지 85% 이상을 달성한다.
- Boundary 계약 테스트는 입력 오류, 출력 포맷, 에러 스키마를 각각 1개 이상 포함하고 모두 통과한다.
- Data 실패 테스트는 설정 파일 없음, 설정 형식 오류, 중복 단위, 잘못된 비율을 포함한다.
- `1 meter = 3.28084 feet`, `1 meter = 1.09361 yard` 기준 비율은 회귀 테스트로 보호한다.
- 새 단위 추가 후 기존 `meter`, `feet`, `yard` 변환 테스트는 수정 없이 통과한다.

### 1.4 비목표(Non-Goal)

- 이 프로젝트는 모든 물리 단위 변환을 지원하지 않는다.
- 이 프로젝트는 GUI, 모바일 앱, 웹 API를 제공하지 않는다.
- 이 프로젝트는 사용자 계정, 데이터베이스 저장, 네트워크 연동을 포함하지 않는다.

### 3.2 기능별 입·출력 계약

| 기능 | 입력 문자열 계약 | 성공 출력 문자열 계약 | 실패 문자열 계약 |
|---|---|---|---|
| 입력 문자열 파싱 | `unit:value` | 단위명과 값이 이후 변환 요청에 사용된다. | `INVALID_FORMAT` 또는 `INVALID_VALUE`를 포함한 오류 문자열 |
| 입력 검증 | `meter:2.5`처럼 단위와 값을 콜론으로 구분한 문자열 | 유효 입력은 변환 단계로 전달된다. | 잘못된 형식은 `INVALID_FORMAT`, 숫자 아님은 `INVALID_VALUE`, 음수는 `NEGATIVE_VALUE` |
| 미지원 단위 처리 | 등록되지 않은 단위가 포함된 `unit:value` | 없음 | `UNKNOWN_UNIT`과 입력 단위명을 포함한 오류 문자열 |
| 기본 단위 변환 | `meter:<number>`, `feet:<number>`, `yard:<number>` | `<sourceValue> <sourceUnit> = <convertedValue> <targetUnit>` 형식의 1개 이상 결과 문자열 | 입력 단위가 미등록이면 `UNKNOWN_UNIT` |
| 원 입력 보존 출력 | 유효한 `unit:value` | 모든 결과 문자열에 원 입력 값과 원 입력 단위가 포함된다. | 입력이 실패하면 변환 결과 문자열을 생성하지 않는다. |
| JSON 출력 | 출력 포맷명 `json`과 유효한 변환 요청 | `sourceUnit`, `sourceValue`, `results` 필드를 포함한 JSON 문자열 | `errorCode`, `message`, `field`, `input`을 포함한 JSON 오류 문자열 |
| CSV 출력 | 출력 포맷명 `csv`와 유효한 변환 요청 | 첫 줄이 `sourceUnit,sourceValue,targetUnit,convertedValue`인 CSV 문자열 | 오류 코드와 메시지를 포함한 CSV 오류 문자열 |
| 표 출력 | 출력 포맷명 `table`과 유효한 변환 요청 | `Source`, `Value`, `Target`, `Converted` 열을 포함한 표 문자열 | 오류 코드와 메시지를 포함한 표 형태 오류 문자열 |
| 설정 로드 | 단위명과 `rateToMeter`를 포함한 설정 문자열 또는 설정 파일 내용 | 로드된 단위 목록이 이후 변환에 사용된다. | 형식 오류는 `DATA_PARSE_ERROR`, 중복 단위는 `DUPLICATE_UNIT`, 잘못된 비율은 `INVALID_RATE` |
| 동적 단위 등록 | `register:<unit>=<rateToMeter>` | 등록 성공 메시지와 갱신된 단위 목록 문자열 | 잘못된 단위명은 `INVALID_UNIT_NAME`, 중복 단위는 `DUPLICATE_UNIT`, 잘못된 비율은 `INVALID_RATE` |

### 3.3 제약 사항

| 항목 | 계약 |
|---|---|
| 기본 기준 단위 | `meter` |
| 기본 지원 단위 | `meter`, `feet`, `yard` |
| 기준 비율 | `1 meter = 3.28084 feet` |
| 기준 비율 | `1 meter = 1.09361 yard` |
| 교차 변환 | feet와 yard 간 변환은 meter 기준을 경유한다. |
| 기본 입력 형식 | `unit:value` |
| 단위명 형식 | 소문자 영문으로 시작하고 소문자 영문, 숫자, 밑줄만 포함한다. |
| 값 형식 | 십진수 숫자 문자열만 허용한다. |
| 소수 파싱 실패 | `meter:2.5.1` 같은 값은 `INVALID_VALUE`로 실패한다. |
| 음수 정책 | 음수 길이는 변환 전에 `NEGATIVE_VALUE`로 실패한다. |
| 0 값 정책 | 0 길이는 유효 입력이며 모든 변환 결과는 0이다. |
| 미지원 단위 | 등록되지 않은 단위는 `UNKNOWN_UNIT`으로 실패한다. |
| 실패 처리 | 실패 입력은 변환 결과 문자열을 생성하지 않는다. |

생성 완료했습니다.
