# UnitConverter_05 Dual-Track 리팩토링 보고서

## 1. 개요

본 보고서는 `UnitConverter_05` 프로젝트에서 수행한 Dual-Track UI + Logic 리팩토링 작업을 정리한다.

작업 목적은 기존 외부 계약을 유지하면서 Boundary(UI Track: 입력 파싱·검증·출력 포맷)와 Domain(Logic Track: 단위 등록·조회·변환 계산)의 책임을 분리하고, Golden Master와 단위 테스트로 출력 및 변환 동작의 회귀를 방지하는 것이다.

## 3. 리팩토링 전 상태

리팩토링 전 `cpp/UnitConverter.cpp`는 단일 파일 안에 입력 파싱, 단위 검증, 변환 비율 보관, 변환 계산, 출력 포맷, 설정 파일 로딩, CLI 실행 흐름이 함께 존재했다.

주요 코드 스멜은 다음과 같았다.

| 항목 | 문제 |
|---|---|
| 입력 파싱 책임 집중 | `parseInput()`이 포맷 검사, 단위명 검증, 숫자 변환, 음수 검증, 등록 단위 확인을 모두 수행 |
| Registry 역할 불명확 | `unitRates()` 전역 map 함수가 단위 저장소 역할을 하지만 명시적인 `UnitRegistry`가 아님 |
| 출력 포맷 책임 혼재 | `formatPlain()`, `formatJson()`이 변환 도메인 코드와 같은 레벨에 존재 |
| 변환 비율 literal 노출 | `3.28084`, `1.09361` 값이 비율 상수로 직접 표현됨 |
| ECB 경계 불명확 | Entity, Control, Boundary 역할이 한 파일 내부에서 명확히 구분되지 않음 |

## 4. 수행한 리팩토링

### 4.1 Boundary: InputParser 분리

`parseInput()`의 기존 공개 계약은 유지하고, 내부 파싱·검증 책임을 `InputParser::parse()`로 이동했다.

| 변경 전 | 변경 후 |
|---|---|
| `parseInput()`이 직접 파싱·검증 수행 | `parseInput()`은 `InputParser`에 위임 |
| Boundary 책임이 공개 함수 본문에 집중 | 입력 파싱 책임을 Boundary 클래스로 명시 |

외부 입력 형식인 `단위:값` 형식과 예외 타입 `std::invalid_argument`는 변경하지 않았다.

### 4.2 Domain: UnitRegistry 명시화

기존 `unitRates()` 전역 map 접근을 `UnitRegistry` 클래스로 캡슐화했다.

| 변경 전 | 변경 후 |
|---|---|
| `unitRates()`가 `std::map<std::string, double>` 참조를 직접 반환 | `UnitRegistry`가 reset, register, lookup, iteration 책임 보유 |
| 단위 저장소 역할이 함수명에만 암시됨 | Domain 저장소 역할이 클래스 이름으로 드러남 |
| `convertAll()`이 전역 map을 직접 순회 | `unitRegistry().units()`를 통해 Registry를 순회 |

새 단위 추가 시 변환 로직을 수정하지 않고 Registry에 단위명과 meter 기준 비율만 등록하는 구조를 유지했다.

### 4.3 Domain: 변환 비율 상수 정리

`3.28084`, `1.09361` literal 문자열을 `cpp/UnitConverter.cpp`에서 제거하고, 의미가 드러나는 상수명으로 정리했다.

| 항목 | 변경 후 |
|---|---|
| meter → feet 비율 | `METER_TO_FEET` |
| meter → yard 비율 | `METER_TO_YARD` |
| feet → meter 비율 | `FEET_RATE_TO_METER` |
| yard → meter 비율 | `YARD_RATE_TO_METER` |

검증 검색 결과 `cpp/UnitConverter.cpp` 내 `3.28084`, `1.09361` 인라인 literal은 더 이상 존재하지 않는다.

### 4.4 Boundary: OutputFormatter 분리

Plain 출력과 JSON 출력 생성 책임을 `OutputFormatter` 클래스로 이동했다.

| 변경 전 | 변경 후 |
|---|---|
| `formatPlain()`이 직접 문자열 조립 | `OutputFormatter::formatPlain()`에 위임 |
| `formatJson()`이 직접 JSON 문자열 조립 | `OutputFormatter::formatJson()`에 위임 |
| 출력 포맷 책임이 독립된 개념으로 드러나지 않음 | Boundary 출력 포맷 책임을 명시 |

기존 공개 함수 `formatPlain()`, `formatJson()`은 유지하여 테스트와 호출부 변경을 최소화했다.

## 5. Dual-Track 분리 결과

| Track | 책임 | 현재 대표 코드 |
|---|---|---|
| Boundary(UI Track) | 입력 파싱, 입력 검증, 출력 포맷, CLI 입출력 | `InputParser`, `OutputFormatter`, `parseInput()`, `formatPlain()`, `formatJson()`, `main()` |
| Domain(Logic Track) | 단위 등록, 단위 조회, meter 허브 변환 계산, 전체 단위 변환 | `UnitRegistry`, `rateToMeter()`, `convert()`, `convertAll()`, `resetDefaultUnits()`, `registerUnit()` |

현재 구조는 아직 단일 `.cpp` 파일 내부에 존재하지만, 책임 단위는 클래스와 함수 경계로 분리되었다. 이후 필요하면 동일한 구조를 유지한 채 `InputParser`, `OutputFormatter`, `UnitRegistry`를 별도 헤더/소스 파일로 이동할 수 있다.

## 7. 커버리지 결과

MSVC `build` 산출물은 `gcov`용 `.gcno/.gcda` 파일을 만들지 않으므로, 별도 GCC/MinGW 커버리지 빌드 디렉터리 `build-gcov`에서 측정했다.

실행 명령:

```powershell
cmake -S . -B build-gcov -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_COMPILER=g++ -DCMAKE_CXX_FLAGS="--coverage -O0 -g" -DCMAKE_EXE_LINKER_FLAGS="--coverage"
cmake --build build-gcov
ctest --test-dir build-gcov --output-on-failure
lcov --capture --directory build-gcov --output-file build-gcov/coverage-all.info
lcov --summary build-gcov/coverage-all.info
```

`UnitConverter.cpp` 기준 집계:

| 범위 | 커버리지 |
|---|---:|
| 전체 | 128/132 = 97.0% |
| Domain | 43/43 = 100.0% |
| Boundary(main 제외) | 77/77 = 100.0% |
| Boundary(main 포함) | 85/89 = 95.5% |

요구 기준인 Domain 95% 이상, Boundary 85% 이상을 충족했다.
