## 8. 발견된 이슈 및 해결 방법

| 이슈 | 원인 | 해결 |
|---|---|---|
| `gcov -o ... tests/test_unit_converter_red.cpp`가 notes 파일을 찾지 못함 | MinGW/CMake가 `test_unit_converter_red.cpp.gcno` 형태로 notes 파일을 생성 | `.gcno`가 있는 디렉터리에서 `gcov -b -c test_unit_converter_red.cpp.gcno` 실행 |
| 워크벤치 루트에 `.gcov` 파일 다수 생성 | 루트에서 `gcov`를 실행하면 현재 작업 디렉터리에 산출물을 생성 | 루트 산출물을 `build-gcov/gcov-root/`로 이동 |
| lcov branch 정보가 `no data found`로 표시 | 현재 lcov 캡처 설정이 line/function 중심으로 수집 | branch 세부 확인은 `gcov -b -c` 결과를 기준으로 판단 |
| CLI 예외 경로 미커버 | Golden Master가 정상 입력 시나리오만 실행 | 실패 입력 CLI 계약 테스트를 다음 단계로 제안 |

## 9. 생성형 AI 활용 회고

| 구분 | 내용 |
|---|---|
| 도움이 된 순간 | RED/GREEN/REFACTOR 흐름을 보고서 구조로 정리하고, gcov 산출물에서 invariant 관련 분기를 빠르게 식별하는 데 효과적이었다. |
| 도움이 된 순간 | branch coverage 보강 후보를 구현 변경 없이 테스트 케이스로만 좁히는 데 유용했다. |
| 한계 | gcov/lcov는 실행 위치와 `.gcno` 파일명 규칙에 민감해서, 한 번의 명령 실패 후 실제 산출물 위치를 기준으로 재실행해야 했다. |
| 한계 | `taken at least once` 수치는 C++ 표준 라이브러리와 예외 throw 경로 영향이 섞여 있어, 제품 코드 invariant와 직접 대응하지 않는 분기가 포함된다. |
| TC 작성 팁 | 실패 계약은 예외 타입만 확인하기보다 가능하면 오류 코드/메시지, exit code, stderr까지 별도 계약으로 고정하는 것이 좋다. |
| TC 작성 팁 | 변환 비율은 `meter` 기준 허브 invariant를 드러내기 위해 `meter→x`, `x→meter`, `x→y`를 함께 둔다. |
| TC 작성 팁 | branch coverage를 올릴 때는 새 구현을 추가하기보다 기존 조건식의 양쪽 경로를 직접 자극하는 입력을 먼저 찾는다. |
